# ECGAgent

ECGAgent は、ecgfeat によって生成される標準的な12誘導 ECG の特徴アーティファクトを対象とした、測定に基づく診断エージェントです。これは研究システムであり、医療機器ではありません。

ランタイム、モデルプロンプト、診断パスウェイ、レポート、トレース、およびバッチ分析アーティファクトは英語のみです。過去の結果ファイルは書き換えられません。

<a id="core-design"></a>
## コア設計

言語モデルは診断推論エンジンです。ecgfeat は、グローバル値、誘導レベル値、ビートレベル値、信頼性フラグ、および監査可能な JSON ポインタを提供する読み取り専用の測定装置です。測定は診断ではなく証拠です。

デフォルトのコンパクトワークフローは、ローカルの27Bクラスモデル向けに設計されています：

1. **計画** — モデルは1つのコンパクトで診断中立な概要を読み、最大3つの候補を支持および反証の観点から提案します。
2. **プログラムによるルーティング** — オーケストレーターは診断固有のパスウェイステップを追加し、重複する観点をマージし、範囲限定されたツール結果をプリフェッチします。
3. **審議** — 決定論的ノードはコードで計算され、モデルは解釈が必要な形態、メカニズム、および鑑別診断に関する質問にのみ回答します。
4. **レンダリングと検証** — コードは両方のノードタイプをマージし、最終的な配置を決定し、引用から真の値を具体化し、レポートをレンダリングし、構造的、意味的、数値的、および証拠ベースの検証を実行します。

従来の5フェーズの台帳ワークフローは、`--diagnostic-workflow legacy` と共に引き続き利用可能です。CLIおよびバッチランナーのデフォルトは `compact` です。

<a id="evidence-rules"></a>
## 証拠ルール

- 患者固有の数値はツール結果から取得され、正確な `ev:/...` 引用を伴う必要があります。
- 値は単位、信頼性、および注意事項と共に具体化されます。
- ツールアクセスとモデルの可視性は別の台帳です。モデルに実際に可視なポインタのみが許可された引用となります。
- 1つのアルゴリズム的チェーンからの候補検出フィールドは、独立した裏付けではありません。
- representative beat は、必ずしも記録全体を代表するものではありません。
- PR間隔の欠如はP波の欠如を意味せず、QT間隔の欠如はT波が情報を持たないことを意味しません。
- 頻度とリズムメカニズムは別々に評価されます。
- 陽性診断には、定義レベルの証拠、形態またはメカニズムが関与する場合は独立した裏付け、および能動的な反証レビューが必要です。

<a id="diagnosis-specific-pathways"></a>
## 診断固有のパスウェイ

各アクティブな候補には、明示的な必須ノード、支持ノード、無効化ノードを持つ短いパスウェイが割り当てられます。ノードは2つの所有者のいずれかを持ちます：

- `owner=program`：ツールによって既に返された閾値、カウント、比率、最小サンプルゲート、シーケンスサマリー、およびその他の決定論的計算。
- `owner=model`：誘導間形態、リズムメカニズム、競合する説明、および矛盾する観察の臨床的解釈。

プログラム所有の範囲には、PRおよびQTの報告可能性と閾値、P-QRS 関連カウント、繰り返される非伝導心房イベント、AVシーケンスサマリー、直接測定された心房および心室頻度、P波軸、RR不整性、QRS 持続時間、形態グループの有病率、早期タイミング、繰り返される広域 QRS シーケンス、低電圧、ペーシングマーカー/キャプチャ/センシング、右前胸電圧関係、および前胸R/S進行が含まれます。

欠落フィールド、不十分な信頼性、または不十分なサンプル数は `unknown` のままです。候補イベントカウントは決してAV伝導比に昇格しません。

<a id="rule-based-second-opinion"></a>
## ルールベースのセカンドオピニオン

コンパクトなワークフローは、デュアルチャンネルの候補プロセスを使用します。モデルはまず、中立的な測定概要から独立した候補を提案します。その計画が固定された後で初めて、プログラムは少量のサニタイズされた ecgfeat ルールベースのセカンドオピニオン候補を追加できます。

ルールのステータスは、支持または反証証拠にはなりません。ルールで追加された候補は、モデル候補と同じ独立した測定パスウェイと偽否定プロセスを完了する必要があります。未審決のルール候補は棄権するか、人間のレビューに送られ、自動的に確認されることはありません。

<a id="available-tools"></a>
## 利用可能なツール

| ツール | 目的 |
|---|---|
| `get_diagnostic_overview()` | 初期計画のためのコンパクトな品質、レート、グローバル間隔、軸、およびモーダリティの可用性 |
| `get_global_table(fields)` | 選択されたグローバル測定値を読み取る |
| `get_measurement(pointer)` | JSON ポインターまたは臨床エイリアスで1つの測定値を読み取る |
| `get_lead_table(fields, leads?)` | リード間で選択されたフィールドを読み取る |
| `get_beat_table(fields, lead?, beat_ids?)` | ビートレベルのリズムまたはリード固有のフィールドを読み取る |
| `search_measurements(query, limit?)` | ポインターが不明な場合に測定名を発見する |
| `get_rhythm_profile(sections?)` | 背景リズム、心房信号、AV関連、前興奮および異常伝導の観察を整理する |
| `get_atrial_event_table(...)` | 心房候補イベントストリームと P-QRS 関連を読み取る |
| `get_p_assessment_table(...)` | P波境界の受容、曖昧さ、および信頼性を確認する |
| `get_morphology_groups(...)` | QRS 形態ファミリーの頻度、連続、およびビート所属を確認する |
| `get_morphology_map(profile, leads?)` | 境界付きクロスリード QRS、ST、または T/U 形態を確認する |
| `get_interval_waveform_context(interval)` | 保持された成分波情報とともに PR または QT/QTc ステータスを確認する |
| `get_pacing_profile(...)` | ペーシングマーカー、キャプチャー、センシング、および証拠の競合を確認する |
| `get_native_beat_profile(profile, leads?, max_beats?)` | Q波、R波の進行、または再分極について、繰り返される自然/非ペーシングビートを確認する |
| `list_findings` / `get_rule_detail` | レガシー審決モードのみ；診断フェーズでは利用不可 |

<a id="english-general-knowledge-layer"></a>
## 英語の一般知識レイヤー

オプションの知識レイヤーは ecgfeat ツールではなく、患者証拠にはなりません。ランタイムナビゲーションは、`ecgagent/knowledge/` 内の簡潔な英語の診断、測定信頼性、および故障モードの参照を使用します。

知識の抜粋は、関係、交絡因子、およびターゲットチェックを提案できます。最終的な結論は、`ev:/...` 引用とともに患者測定値に戻らなければなりません。臨床ルールのソース、Philips DXL、グラスゴー、および機能ブループリントは、患者レベルのランタイムプロンプトから除外されます。

<a id="reports-and-traces"></a>
## レポートとトレース

すべての成功した実行は、以下を生成できます：

- `diagnoses/<record>.json` — 構造化された判決、検証、および監査データ
- `diagnoses/<record>.md` — 詳細な英語解釈レポート
- `brief_reports/<record>_brief.md` — 簡潔な英語の結論、証拠、制限事項、および推奨事項
- `agent_traces/<record>_agent_trace.md` — フェーズ出力、モデル可視ツールコンテキスト、完全な生ツール監査、検証、およびランタイム使用状況

レポートは構造化された判決から決定論的にレンダリングされます。結果をパラフレーズするセカンドモデルはありません。

<a id="run-one-record-with-a-local-qwen-server"></a>
## ローカル Qwen サーバーで1つのレコードを実行する

vLLM を別々に開始し、次に実行します：

```bash
cd /workspace/ecg_gemma

.venv/bin/python -m ecgagent.cli \
  --features /workspace/ecg_gemma/ptbxl_09000_ecgfeat/features/09025_hr_features.json \
  --record-id 09025_hr \
  --agent \
  --backend qwen-local \
  --model qwen3.8-27b \
  --qwen-base-url http://127.0.0.1:8000/v1 \
  --diagnostic-workflow compact
```

Qwenのバックエンドは、OpenAI互換の`tools`および`tool_calls`を使用しています。コンパクトモードでは、オーケストレーターがツールビューをプリフェッチするため、Qwenはツール呼び出しを生成する必要がありません。厳格なJSONスキーマデコーディングは、計画と最終審決の両方を制約します。

<a id="batch-diagnosis"></a>
## バッチ診断

```bash
cd /workspace/ecg_gemma

.venv/bin/python -m ecgagent.batch diagnose \
  --output-dir /workspace/ecg_gemma/qwen_agent_output/qwen_english_run \
  --backend qwen-local \
  --model qwen3.8-27b \
  --qwen-base-url http://127.0.0.1:8000/v1 \
  --diagnostic-workflow compact \
  --agent-workers 2 \
  --verbose
```

参照ラベルはエージェントの診断が完了した後にのみ結合され、モデルのコンテキストには決して含まれません。

<a id="context-controls-for-local-models"></a>
## ローカルモデルのコンテキスト制御

長い `ev:/...` ポインタは、Qwen コンテキスト内で `Q1` のような安定した短い参照に投影され、`V2.t_amp_mv` や `global.qrs_ms` などの意味ラベルは保持されます。プログラムコードは最終検証前に元のポインタを復元します。

ツール結果は、引用、値、単位、信頼性、および注意事項を含む完全な証拠アトムとしてパックされます。パック処理はアトムの境界でのみ切り捨てられ、ツール、リード、ビート、およびイベントセクション間で公平にローテーションされます。完全な生データはトレースで引き続き利用可能です。

フェーズ内の同一のツールおよび引数呼び出しは重複排除されます。レコード全体の制限は、モデルのターン数、トークン使用量、経過時間、および連続する `max_tokens` 切り捨てを制限します。

<a id="validation-boundary"></a>
## 検証境界

決定論的な検証は、出力構造、引用の認可、正確な値と単位、信頼性の資格、数値比較、診断コードの配置、および選択された定義レベルの矛盾をチェックします。診断を作成することはなく、データセットラベルや臨床ルールの結論を読み取ることもありません。

すべての陽性所見、ダウングレードされた所見、および品質ゲートを通過しなかった結果は、資格を持つ人間のレビューが必要です。ECGAgent の出力は、元の波形、臨床歴、症状、以前の検査、または公式な医療診断に取って代わるものではありません。
