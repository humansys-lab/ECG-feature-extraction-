# P波関連の再実行結果分析

分析対象：`ludb_full_compare` の現在の再実行結果。

結果のタイムライン：

- `ludb_full_compare/summary.csv` の更新時刻：2026-07-05 16:55。
- 200件の `*_features.json` がすべて生成済み。
- 新規フィールドが結果に反映済み（例：`p_offset_consensus_index`、`p_dur_consensus_ms`、`pr_segment_consensus_ms`、`p_boundary_consensus_source`）。

<a id="1-总体结论"></a>
## 1. 総合結論

今回のP波関連の修正は有効に機能しており、特に **raw limb PRがQRS付近の偽P波によって短く見積もられた** 症例群に対して顕著な改善をもたらした。しかし、全データベースのPR指標全体としては顕著な改善は見られず、第1段階の保守的なコンセンサスアプローチが一部のシナリオのみを解決し、残りの外れ値（アウトライア）は依然としてP onsetクラスターの選択、PR core rescueの過剰適用、P軸/P波形の不安定性などの問題に集中していることを示している。

最も重要な観察点：

1. **PRコンセンサスゲートは価値がある。**
   現在のactual global PRのMAEは`17.02 ms`である。現在のfeaturesを用いてraw limb medianベースラインを逆算すると、MAEは約`26.82 ms`となる。つまり、グローバルな集約/レスキューパスは確かに一部の症例を救っている。

2. **しかし、現在の全データベースPR指標には依然として軽微な負のバイアスがある。**
   現在のPRバイアスは`-12.02 ms`、median diffは`-10 ms`であり、P onsetが依然として全体的に遅めであることを示している。

3. **P offsetコンセンサスのカバレッジは良好だが、raw morphologyを直接置き換えるべきではない。**
   ビートレベルの`p_offset_consensus_index`は、リード・ビート行の約`59.91%`をカバーしている。representativeレベルのP durationコンセンサスmedianは約`80 ms`である。しかし、短すぎる/長すぎる外れ値が依然として存在し、例えばrecord 57のコンセンサスP durationは`152 ms`に達する。

4. **P軸は依然として顕著な弱点である。**
   P軸のMAEは約`24.25°`であり、絶対誤差が`90°`を超える記録が14件ある。この部分は主にPRコンセンサスでは解決できず、P極性、P符号付き面積、低振幅P波、およびリードのサポート度合いの問題である。

5. **P欠損率の高い記録が依然として多い。**
   例えば、record 104、45、111、90、34、74のアルゴリズムP欠損率はすべて高い。これらは単なるonset/offset境界の問題ではなく、P波の存在有無/低振幅P波/リズム文脈の問題に近い。

<a id="5-失败模式分类"></a>
## 5. 故障モードの分類

<a id="51-长-pr-没救够"></a>
### 5.1 長い PR だけでは十分ではありません

代表記録：23、39、40、49、61、73、75、102、120、130。

パフォーマンス:

- 生の四肢の中央値は GT よりも大幅に短い。
- `pr_consensus_ms` は長い方向に PR をプルできますが、多くのレコードは依然として GT より 30 ～ 60 ミリ秒短いです。
- `p_onset_consensus_spread_ms` は多くの場合非常に大きく、複数のリード発症候補の深刻な断片化を示します。

根本原因の判断:

現在の発症のコンセンサスは依然としてすべての発症の比較的粗い集合体であり、実際の発症クラスタの選択が欠けています。最新の偽の P は回避されますが、複数の P オンセット クラスターがある場合、「以前の真の」長い PR クラスターがまだ安定して選択されません。

次に何をすべきか:

- 全体的な発症の広がりを記録するだけでなく、クラスターレベルのコンセンサスを発症の開始に追加します。
- 発症クラスターごとに、サポート、リード領域、クラスター中心、代表者からの距離を事前に記録します。
- 長い PR シナリオでは初期のクラスターを選択できますが、複数のリード波形と代表的な波形をサポートする必要があります。

<a id="52-短-pr-假-p-仍主导"></a>
### 5.2 ショート PR 偽 P が依然として優勢です

代表記録：130、64、22、180、27、9、29。

パフォーマンス:

- `pr_consensus_ms` も短く、融合 P ピーク/オンセットが QRS に近い誤った偏向にロックされていることを示します。
- P オフセットのコンセンサスは安定しているように見えるかもしれませんが、これは誤った P 波に基づく安定です。

根本原因の判断:

これは「偽のコンセンサス」です。複数のリードがすべて、一貫したタイミングで、QRS に近い小さな変動で候補を見つけます。これはコンセンサスのように見えますが、実際の P 開始ではありません。

次に何をすべきか:

- P ピーク フュージョンは、ピーク インデックスを出力するだけでなく、候補クラスターも出力する必要があります。
- 短い PR クラスターが長い PR クラスターと競合する場合、振幅/時間の一貫性のみに基づいて選択することはできません。
- PR セグメント、P 期間、リード領域、事前の代表テンプレートを共同スコアリングに追加する必要があります。

<a id="53-pr-被救得过长"></a>
### 5.3 PR の保存期間が長すぎました

代表記録：57、182、139。

レコード57:

- 生の四肢の中央値 = 225 ミリ秒、GT = 139 ミリ秒。
- `pr_consensus_ms = 102ms` は、適切に保護されている現在のゲートによって拒否されます。
- しかし、生の四肢 PR はまだ長すぎます。これは、誤った早期 P / T テール汚染を特定する必要があり、短いコンセンサスを防ぐだけではないことを示しています。

レコード182:

- 生の四肢の中央値は約 113.5 ミリ秒です。
- コンセンサス中央値は約 109 ミリ秒。
- 最終アルゴリズム PR = 202.12ms。
- これにより、後続の `_physiologic_pr_core_from_beats(...)` または API レイヤ PR レスキューによって PR が過剰に拡張されることがプロンプトされます。

レコード139:

- 生の四肢の中央値は約 206 ミリ秒、GT = 162 ミリ秒。
- コンセンサスの中央値は約 124 ミリ秒。
- raw は長すぎ、コンセンサスは短すぎ、実際の値は中間にあります。

次に何をすべきか:

- 現在の PR <120 或 >240 だけを理由に PR コア レスキューを上書きすることはできません。生のリード中央値、コンセンサス中央値、開始クラスターがサポートされているかどうかを確認する必要があります。
- 順方向外れ値に対する保護の追加: 生の PR が非常に長いが、コンセンサス/オフセット/P 期間が別のクラスターを示唆する場合、生のリム中央値を直接信頼することはできません。
- 生またはコンセンサスの代わりに、「中間クラスター」戦略が必要です。

<a id="7-建议下一轮修改优先级"></a>
## 7. 次のラウンドで優先度を変更することをお勧めします

<a id="p0给-p-onset-做真正-cluster-consensus"></a>
### P0: 開始に向けて実際のクラスターのコンセンサスを作成する

現在、P offset クラスターがありますが、P onset には選択されたクラスターの来歴がまだありません。次のステップでは、以下を追加する必要があります。

- `p_onset_cluster_center_index`
- `p_onset_cluster_support`
- `p_onset_cluster_spread_ms`
- `p_onset_cluster_leads`
- `p_onset_cluster_rank`
- `p_onset_consensus_reason`

目標は、以下を区別することです。

- QRS 付近の短い PR クラスター。
- より早期の真の開始クラスター。
- T テール/ベースライン ドリフト クラスター。

<a id="p1限制-pr-core-rescue-过度覆盖"></a>
### P1: PR コアレスキューの過剰なカバレッジを制限する

レコード 182 は、その後の PR レスキューにより、元々短かった raw/コンセンサス PR が 202 ミリ秒まで長くなる可能性があることを示しています。提案:

- 生の四肢中央値と `pr_consensus_ms` が両方とも 100 ～ 130 ミリ秒以内にある場合、明確なマルチリードの長い PR オンセット クラスターがない限り、PR コア レスキューは >180 ミリ秒を直接カバーすべきではありません。
- PR コアレスキューでは、`pr_source=physiologic_pr_core_rescue` などの出所を記録する必要があります。
- レスキュー前後の差が 50ms を超えるレコードのデバッグ フィールドを出力します。

<a id="p2对正向-pr-outlier-做-false-early-plong-pr-识别"></a>
### P2: フォワード PR 外れ値に対して誤った早期 P/ロング PR 識別を行う

レコード 57/139 では、生の四肢 PR が初期の偽 P によって伸長する可能性があると説明しています。

- 生の PR が非常に長いが、コンセンサス P 期間/PR セグメントがより短いクラスターをサポートしている場合は、最初に生の長い PR をダウングレードします。
- ショートコンセンサスを直接使用せず、クラスタースコアリングを使用して中間の信頼できるクラスターを選択します。

<a id="p3p-offset-consensus-加-confidence不直接进-morphology"></a>
### P3: P オフセットのコンセンサスと信頼度。形態学を直接入力しないでください。

以下を追加することをお勧めします。

- `p_offset_consensus_confidence`
- `p_duration_consensus_reliable`
- `p_boundary_consensus_reject_reason`

ルール:

- サポート < 4: 信頼度が低い。
- オフセットスプレッド > 35 ～ 40ms: 信頼性が低い。
- P 持続時間 <60ms 或 >140ms: 特別な形式でサポートされていない限り、信頼性が低くなります。

<a id="p4p-axis-单独修"></a>
### P4: P軸は別途修理します

P 軸は PR とは異なるため、別のラウンドに存在する必要があります。

- 代表/テンプレート P 署名領域を使用します。
- 四肢誘導 P 極性の一貫性を追加します。
- 少量のリードの重量を軽減します。

## 9. まとめ

この再実行は、最初の段階の方向が正しいことを証明します。P 境界コンセンサスと PR コンセンサス ゲートにより、明らかな P 開始が遅い/短い PR 外れ値のバッチを保存できます。レコード 39 が最も典型的な例です。
