<a id="1-数据概况"></a>
## 1. データの概要

- `summary.csv` 合計 200 レコード。
- 各レコードには、測定コントラスト、グローバル間隔/軸コントラスト、拍動/欠損/質量数を表す 12 個のリードが含まれています。
- リードごとの比較テキストは、`PR/QRS/QT/QTcB/R/T/ST-J` を含む合計 16,800 行のインジケーターに解析されます。

全体的に、現在のアルゴリズムの R ピーク/HR 基本機能は比較的安定しており、主なエラーは以下に集中しています。

1. PR/P 波の境界と PR の利用可能性。
2. QRS オンセット/オフセット、特にワイド QRS、ペーシング、ターミナル スラー。
3. T エンド/QT レスキューまたは低サポート パス。
4. QTのばらつきが大幅に抑制されます。
5. 軸およびリードごと/グローバル比較に評価基準の問題があります。

<a id="3-beat-检测与质量计数"></a>
## 3. ビート検出と品質カウント

通常、アルゴリズムには GT よりも多くのビートがあります。

- 平均 `algorithm_beats - ground_truth_beats = +1.645`。
- 中央値は `+2` です。
- 138/200 の記録は GT よりちょうど 2 ビート大きいです。
- これは、最初と最後で異なるビート包含ルールが原因である可能性が高く、アルゴリズムには 10 秒レコードの端のビートも含まれており、GT レポート/サマリーは完全な測定可能なビートのみをカウントする可能性があります。

HR は主に RR 中央値/内部拍動によって決まるため、これは通常、HR にはほとんど影響しません。しかし、それは汚染します：

- `algorithm_total` vs `ground_truth_total`
- 欠落カウント
- 信頼性の低いカウント
- レコードごとの品質の割合

最初にビート マッチング/ウィンドウ アライメントを評価スクリプトに追加することをお勧めします。

- グローバル人事は引き続き独立して評価できます。
- ビートレベルが見つからない/信頼できない場合は、GT と一致するビートのみを比較する必要があります。
- 先頭と末尾の不完全ビートは、両側から除外されるか、エッジビートとして個別にリストされます。

<a id="4-p-波与-pr需要优先改"></a>
## 4. P 波と PR: 最初に変更する必要があります

現象:

- グローバル PR バイアス = `-11.77 ms`、MAE = `16.85 ms`。
- 44/151 PR には 20 ミリ秒を超える誤差があります。
- リードごとの PR はより明白です: バイアス = `-21.72 ms`、MAE = `28.31 ms`。
- 最大の PR エラーを持つ誘導は V3/V4/V5、III、aVR などに集中しており、低振幅/複雑な P 波の開始がアルゴリズムによって遅延される可能性が高いことを示しています。
- アルゴリズムには 48 個の PR と 25 個の GT が欠落しています。言い換えれば、このアルゴリズムの心拍レベル `P missing` は GT よりも低いですが、主に P が信頼性の低いものとしてマークされているか、心房測定が抑制されているため、PR の可用性は悪くなります。

典型的な外れ値:

- レコード 39: PR `-88 ms`
- レコード 57: PR `+86 ms`
- レコード 130: PR `-84.5 ms`
- レコード 120: PR `-61 ms`

根本原因の判断:

1. 開始はほとんどの場合遅く、結果的に PR が体系的に短くなります。
2. 長い PR/低振幅 P/P が T またはフラッター状の残差と混同されると、現在の信頼性ルールでは簡単にグローバル PR が N/A になります。
3. マルチリード P アンカーは PR 要約を十分に保護しません。特に、一部のリードの P 波が明確でも他のリードが信頼できない場合、全体的な PR が過度に抑制されます。

提案される改善点:

1. P オンセットの早期レスキューを強化する: 安定した P ピークがすでにある拍動の場合は、シングル リードのタンジェントのみに依存するのではなく、マルチリード心房アンカーを使用して一貫したオンセットを予測します。
2. PR サマリーは、信頼性を得るために同時に多くの見込み客を必要としません。四肢誘導優先と V1 支援を備えた堅牢な PR を使用できます。
3. ロング PR シナリオの P ルックバック/早期開始制限を緩和し、ロング PR レスキューのトリガー条件をシングル リードからマルチ リードの一貫性に変更します。
4. 評価は `P detected`、`P reliable`、`PR globally reportable` の 3 段階に分かれています。

<a id="5-qrs-onsetoffset宽-qrs起搏和-terminal-slur-是主要风险"></a>
## 5. QRS オンセット/オフセット: 広い QRS、ペーシングと末端のスラーが大きなリスク

グローバル QRS:

- バイアス = `+5.73 ms`
- MAE = `9.88 ms`
- 17/200 エラーが 20 ミリ秒を超えました。

典型的な外れ値:

- レコード 108: QRS `-46 ms`
- レコード 90: QRS `+44.5 ms`
- レコード 99: QRS `+35.5 ms`
- レコード 5: QRS `+32 ms`
- レコード 8: QRS `+28.9 ms`

視覚的な確認:

- レコード 108: アルゴリズム QRS オフセットは一部のリードで GT よりも大幅に早く、終端 QRS/スラーを切断し、ST-J 偏差が発生します。たとえば、V1 ST-J 偏差は `+0.59 mV` に達します。
- レコード 8: QRS 検出器の信頼性は非常に低く、中央値は約 `0.049` であり、ペーシング スパイク メタデータが疑われる。グローバル ルートは `wide_qrs_jt` に入り、QRS/QT が影響を受けます。
- レコード 74: ペーシング/低振幅 QRS シーン、アルゴリズムは 5 ビートのみを検出し、GT は 9、HR は約 60 bpm から約 30 bpm に変化します。

根本原因の判断:

1. QRS 端子境界は、幅の広い QRS、低振幅端子スラー、および ST/T ジャンクションの影響を受けます。
2. ペーシングおよび低振幅 QRS では、R 検出器の信頼性が非常に低い場合でも、後続の測定値が入力されるため、周波数が半分になったり、グループ化が間違ったりしやすくなります。
3. QRS オフセット エラーは、ST-J、JT、QT パス、wide_qrs_jt パスを直接汚染します。

提案される改善点:

1. QRS 検出器の信頼性が低いレコードにマルチリードフォールバックを追加します。複数のリードが予想される RR 付近で同期した偏向を持っている限り、ビートが見逃されることはありません。
2. ペーシング シーンにスパイク アンカー キャプチャ検索を追加しました。通常の検出器に依存するのではなく、ペーシング スパイク後の固定生理学的ウィンドウから QRS を見つけてキャプチャします。
3. QRS オフセット コンセンサスでは、ターミナル スラー/ST-J ガードを導入する必要があります。オフセット後の `ST40/ST80` がポイント J と大きく異なる場合は、オフセットが早すぎるか遅すぎるかを判断するためにバックトラックする必要があります。
4. 広い QRS ルートは、QT/JT に影響を与えるだけでなく、QRS オフセットの信頼性を逆に制限する必要があります。

<a id="6-t-endqt主路径可用rescue-和-low-support-路径需要收紧"></a>
## 6. T エンド/QT: メイン パスは利用可能ですが、レスキュー パスと低サポート パスを強化する必要があります

全体的な QT:

- バイアス = `-1.09 ms`
- MAE = `13.58 ms`
- 25/200 エラーは 30 ミリ秒を超えます。

QT ソースごとにグループ化:

| QT ソース |レコード数 |バイアス |前 | P75腹筋 |最大腹筋 |
|---|---:|---:|---:|---:|---:|
|信頼できる_リード_メディアン | 125 | +5.1ミリ秒 | 9.6ミリ秒 | 11.5ミリ秒 | 63ミリ秒 |
| low_qt_support_fallback | 36 | -5.9ミリ秒 | 20.9ミリ秒 | 28.4ミリ秒 | 81ミリ秒 |
| Reliable_raw_qt_cluster_rescue | 25 | -13.8ミリ秒 | 16.1ミリ秒 | 10.5ミリ秒 | 91.5ミリ秒 |
| raw_qt_core_rescue | 8 | -27.3ミリ秒 | 29.3ミリ秒 | 47ミリ秒 | 58ミリ秒 |
| Wide_qrs_low_support_qt_fallback | 4 | -20.6ミリ秒 | 28.6ミリ秒 | 30.6ミリ秒 | 73ミリ秒 |

結論は明らかです。

- `reliable_lead_median` メイン パスのパフォーマンスが最も優れています。
- `low_qt_support` およびさまざまな救助経路は大幅に悪化し、全体的に短くなります。
- 大きな QT 外れ値には、ほとんどの場合、`st_t_confusion`、`t_end_fallback`、`beat_unreliable`、またはレスキュー ソースが付属します。

典型的な外れ値:

- レコード 57: QT `-91.5 ms`。この図から、アルゴリズムによって T offset が早期に切り捨てられることがわかります。
- レコード 73: QT `-81 ms`。
- レコード 125: QT `-73 ms`。
- レコード 81: QT `-72.5 ms`。
- レコード 133: QT `-68.5 ms`。
- レコード 24: QT `+63 ms`。

提案される改善点:

1. レスキュー/ローサポート QT パスに、T ピーク後の最短テール、T エリアテール、クロスリードレイトテールサポートなどの「途中で終了しない」制約を追加します。
2. `st_t_confusion` が表示された場合、初期の谷を直接 T 端とみなさないでください。まず、後続の同極性または二相性の T 波尾を探します。
3. `t_end_fallback` のビートについては、基本範囲を通過する限り、グローバル中央値に入る代わりに、グローバル QT への参加の重みを減らします。
4. 広い QRS/JT パスでは、QT は JT の合理性に依存するだけでなく、QRS オフセットが信頼できるかどうかもチェックします。

<a id="7-qt-dispersion当前明显低估"></a>
## 7. QT 分散: 現在明らかに過小評価されています

QT分散：

- バイアス = `-25.35 ms`
- MAE = `27.83 ms`
- 49/190 項目が 40 ミリ秒を超えました。

これは非常に安定したシステム上の問題です。その理由は、単一の T エンドの外れ値ではありませんが、現在の代表的なリード/コンセンサス戦略では、複数のリードの QT が同様の値に引き下げられ、リード間の差異が圧縮される傾向があります。

典型的な外れ値:

- レコード 132: `-112 ms`
- レコード 29: `-101 ms`
- レコード 21: `-99 ms`
- レコード 84: `-97 ms`
- レコード 52: `-94 ms`

提案される改善点:

1. QT 分散は、各リードを入力した後、グローバル `qt_consensus_ms` ではなく、独立したリードごとの QT を使用して計算する必要があります。
2. リードごとに 3 つの値セット（独立 QT、コンセンサス QT、グローバル QT に使用）を保持します。
3. 分散を計算するときは、明らかに無効なリードのみをフィルタリングし、すべてのリードをグローバル T エンドに強制的に揃えないでください。
4. レポートに分散源を明記します: `independent_lead_qt` または `consensus_qt`。

<a id="8-axis算法问题和评估问题混在一起"></a>
## 8. 軸：アルゴリズム問題と評価問題が混在

軸インジケーターは注意して解釈する必要があります。

- P 軸 MAE = `24.25 deg`、最大差 = `228.83 deg`。
- T 軸 MAE = `16.60 deg`、最大差分 = `352.21 deg`。
- これらの最大値には、角度の回り込みの問題が含まれる可能性が高くなります。 -179 度から 179 度を直接減算すると 358 度になりますが、臨床的な角度の差は 2 度である必要があります。

同時に、アルゴリズムの T 軸には 50 個の項目が欠落していますが、GT T 軸には欠落していません。これはアルゴリズムの使いやすさの問題です。

提案される改善点:

1. 比較スクリプトは、軸の差を計算するときに円角度差を使用する必要があります: `min(abs(a-b), 360-abs(a-b))`。
2. T 軸集約は、すべてのリード T が信頼できるかどうかに過度に依存すべきではありません。主肢リードが利用可能な T 振幅を持っている限り、信頼性は低いが報告可能な T 軸が与えられるはずです。
3. P 軸が大きな外れ値である場合、円差分を修正した後に再順序付けし、真の P 波の方向が間違っているか、比較開口が間違っているかを判断する必要があります。

<a id="9-st-jtr-amplitude"></a>
## 9. ST-J/T/R振幅

リードごとの振幅の全体的なパフォーマンスが向上しています。

|指標 |バイアス |前 | P75腹筋 |最大腹筋 |
|---|---:|---:|---:|---:|
| R振幅 | -0.005mV | 0.023mV | 0.03mV | 0.51mV |
| T 振幅 | +0.003mV | 0.035mV | 0.03mV | 0.81mV |
| ST-J | -0.004mV | 0.029mV | 0.03mV | 0.68mV |

これらのメトリクスのパフォーマンスの中央値は問題ありませんが、著しく外れ値です。

- 記録 116: T/ST-J 極性またはベースライン レベルの大きな偏差を示す複数の四肢誘導。
- レコード 108: ST-J の QRS オフセット切り捨てからの大きな偏差。
- レコード 35/116: 大きな T 振幅外れ値は、主に T 極性/選択エラーによって引き起こされます。

提案される改善点:

1. ST-J 外れ値は、ST-J サンプリングのみを調整するのではなく、QRS オフセットとベースラインからの変更を優先します。
2. T 振幅外れ値は、T 極性/T 候補の選択とともに変更する必要があります。
3. ST-J が生理学的範囲を超え、QRS 最終信頼度が低い拍動の場合、体重は自動的にダウングレードされるか、測定値が信頼できないとしてマークされます。

<a id="10-报告比较脚本本身需要改"></a>
## 10. レポート/比較スクリプト自体を変更する必要があります

現在の比較テキストには、混合口径に関するいくつかの問題があり、手動による判断に影響します。

1. リードごとのテーブルの多くの QRS/QT 値は、リード 12 でまったく同じです。これは、真に独立したリードごとの値ではなく、コンセンサス/グローバル値を比較している可能性があることを示しています。
2. 一部のレコードのグローバル測定とリードごとの比較が矛盾しています。
   - レコード 8: グローバル QRS は `144.4 ms` で、リードごとのテーブルの QRS は `204 ms` です。
   - レコード 109: グローバル QT は `305 ms` で、リードごとのテーブルの QT は `492 ms` です。
3. 軸の差分は循環正規化を実行しないため、一部の外れ値が誇張されます。

最初に比較/レポート ハーネスを修復することをお勧めします。

1. リードごとに明確な分離を示します。
   - `raw_independent`
   - `lead_representative`
   - `consensus`
   - `global_used`
2. 概要のグローバル インジケーターは、同じソースからの GT グローバル インジケーターとのみ比較されます。
3. リードごとのインジケーターは、リードごとの GT とのみ比較されます。グローバルコンセンサスを各リードにコピーしてリードごとの測定値として使用しないでください。
4. 軸差分は円周距離を使用します。

<a id="11-改进优先级"></a>
## 11. 優先順位を改善する

<a id="p0先修评估口径"></a>
### P0: 前提条件となる評価基準

これらが修復されない場合、その後のアルゴリズム パラメーターの調整が誤ったものになります。

1. 軸差分は円差分を使用します。
2. ビート レベルの比較はビート マッチングに使用され、最初と最後のエッジ ビートは個別に処理されます。
3. 各リードに対するコンセンサス値の繰り返しの比較を避けるため、リードごと/グローバルソースを分離します。
4. QT 分散は、独立したリードごとの QT を使用して再評価されます。

<a id="p1修起搏低幅-qrs-detector"></a>
### P1: ペーシング/低振幅 QRS 検出器を修復します

対象となるケース：

- 74
- 8
- 83
- 99
- 110

目標:

- HR の半分の周波数/検出漏れを排除します。
- QRS 検出器の信頼性が非常に低い場合は、マルチリードフォールバックに入ります。

<a id="13-当前结论"></a>
## １３．現時点での結論

現在のアルゴリズムのバックボーンは、最も一般的な LUDB で記録された HR/QRS/QT 測定を安定して完了できます。最も価値のある投資は、完全な書き換えではなく、まず口径と境界の外れ値を評価することです。

短期的に最も費用対効果の高いルートは次のとおりです。

1. まず、比較/レポートのハーネスについて学習します。
2. ペーシング/低振幅 QRS の検出欠落を修復します。
3. 次に、QRS 端子境界を修復します。
4.次にTエンドレスキュー/ローサポートを修正します。
5. 最後に、システムは P onset/PR および軸の可用性を調整します。
