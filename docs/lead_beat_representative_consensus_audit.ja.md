# リードごと/ビートごと、代表的な波形とマルチリードのコンセンサス利用状況の監査

分析オブジェクト:

- 現在のコード: `feature_extraction/ecgfeat`
- キーの例: `ludb_full_compare/5/5_features.json`
- 対象となる質問: 各波形、各セグメント、および各特徴が、「まず各リードと各ビート、次に代表的な波形を合成し、次にマルチリードのコンセンサスを使用する」という測定戦略に正しく準拠しているかどうか。

<a id="1-总体结论"></a>
## 1. 全体的な結論

現在のアーキテクチャにはすでに 3 つの情報層があります。

1. `beat_features`: 各 `lead × beat` の P/QRS/T/ST/間隔/形態を個別に測定します。
2. `representative_leads`: リード別にまとめられた代表的なリードパラメータ。
3. `*_consensus_ms` および `global_features`: クロスリードコンセンサスの後のグローバル間隔。

ただし、利用方法はまったく同じではありません。

- QRS/QT グローバル インターバルは、マルチリード コンセンサスを最大限に活用します。
- P/PR セクションでは、誘導ごと、心拍ごと、および肢誘導ごとの要約が使用されますが、波形と誘導間 P オンセットのコンセンサスが十分に活用されていません。
- ST セグメントに生の再測定パスが追加されました: QRS オフセット生の修復。ビートレベル J のコンセンサスの後、リスクの高い ST-J/ST40/ST80 が再テストされます。ただし、代表テンプレート ST 測定にはまだ改善の余地があります。
- QT 分散 リードごとに独立した QT が使用されますが、コア クラスターが選択されるため、リード間の分散を容易に低減できます。
- 代表的な波形は現在、多くの場合 medoid シングル ショットであり、必ずしもマルチショットの平均/中央値テンプレートではないため、ノイズの低減と境界の改善への貢献は限られています。
- レポート/比較には、生、代表、コンセンサスが混在して使用されているため、アルゴリズム自体の判断を誤りやすくなります。

言い換えれば: **フレームワークの方向性は正しいですが、「代表的な波形」と「マルチリードコンセンサス」はまだすべての波形/セグメントで一貫して追跡可能な方法で完全には活用されていません。 **

<a id="2-当前流水线是否符合目标结构"></a>
## 2. 現在のパイプラインがターゲット構造に準拠しているかどうか

<a id="21-已经做到了的部分"></a>
### 2.1 これまでに行われたこと

メインプロセスは `feature_extraction/ecgfeat/api.py` にあります。

1. 最初に多リード QRS/R ピーク検出を実行します。
2. 次に、R ピークを押してビートを作成します。
3. ビート上でモルフォロジーグループ化を実行します。
4. グループごとに representative beat を構築します。
5. `delineate_beats()` は、ビート×リードごとに境界と特徴を個別に抽出します。
6. `delineate_beats()` は内部で `_apply_multilead_consensus()` を実行し、`qrs_consensus_ms`、`pr_consensus_ms`、および `qt_consensus_ms` を書き込みます。
7. 測定値 representative beat を再度構築し、この代表ビートに対して再度描写を実行します。
8. `build_representative_lead_features()` は、選択したビートと representative beat の特徴を各リードの代表的なパラメーターに要約します。
9. `compute_global_features()` は、代表的なリードとビートの特徴からのグローバル PR/QRS/QT/軸/分散を要約します。

対応するコードの場所:

- `api.py:1303-1420`: QRS 検出、グループ化、代表波形、ビート×リードの描写。
- `api.py:1474-1506`: representative beat で再構成された代表的なリード特徴の測定。
- `delineate.py:1964`：拍×リードごとにP/QRS/T/ST抽出。
- `delineate.py:1596`: 複数のリードのコンセンサス。
- `features.py:348`: 代表的なリード フィーチャを構築します。
- `features.py:2001`: グローバル フィーチャを計算します。

<a id="22-关键限制"></a>
### 2.2 主な制限事項

現在、representative beat は必ずしも「マルチショット平均テンプレート」であるわけではありません。 `build_representative_beats_with_meta()` は、アライメント、ファミリー クラスタリング、外れ値の除外を行ってから、ファミリー medoid を優先します。 medoid が存在する場合は、`used_count=1`。

レコード 5:

- `member_count = 9`
- `outlier_count = 1`
- `used_count = 1`

これは、代表的な波形が実際には「代表的な単一ビート」であり、8 つのクリーンなビートの中央値/平均テンプレートではないことを示しています。このデザインは真の形状を保持できますが、ノイズ低減能力は中央値テンプレートほど良くありません。

将来的には、次の 2 種類の代表者を保持することが推奨されます。

- `medoid_template`: 形態学的分類、Q/R/S/ノッチ/スラーなどに使用されます。
- `median_template`: P オンセット、QRS オンセット/オフセット、T エンド、ST セグメントなどの境界および低ノイズ測定用。

<a id="3-各波形segment-的利用情况"></a>
## 3. 各波形/セグメントの利用

<a id="31-p-波与-pr-segmentpr-interval"></a>
## 3.1 P 波と PR セグメント/PR インターバル

現在の実践:

- 各リード×ビートは独立して P オンセット/ピーク/オフセットを検出します。
- ノッチ、二相、終末陰性、PTF-V1 などの P 形態は、各心拍×誘導で測定されます。
- 代表的なリードを要約する場合、P の振幅/面積/形態が representative beat 特徴よりも優先されます。そうでない場合は、プールされた拍の中央値が採用されます。
- PR 間隔は、代表波形ではなく代表リードのプールされた中央値を優先的に取得します。
- グローバル PR は、四肢リードの優先順位中央値を使用し、生理学的 PR コア レスキューを備えています。

利点:

- P 形態では、P 波形態の安定化に役立つ代表的な波形が利用されています。
- グローバル PR は、PR を短くする V リードや誤った P を避けるために、すべての事前記録リードを盲目的に使用しません。
- レコード 5 では、グローバル PR は 130 ミリ秒、GT は 138 ミリ秒、誤差はわずか -8 ミリ秒であり、この例ではコア レスキューが有効であることを示しています。

短所:

- PR/P の発症は依然として体系的に不足するリスクにさらされています。前の概要の PR バイアスは約 -11.77 ミリ秒でした。
- 波形が PR 間隔のメインパスとして使用されていないことを示します。間隔では、最初にプールされた中央値が使用されます。
- マルチリード オンセット コンセンサスは `pr_consensus_ms` のみを書き込みますが、グローバル PR は主に `_global_pr_median()` のリードごとの PR を引き続き使用し、`pr_consensus_ms` を優先しません。
- 低振幅 P または長い PR では、代表波形の SNR の利点が完全に解放されません。

提案:

1. P 波用に 3 セットのランドマーク `p_on_independent`、`p_on_template`、および `p_on_consensus` を予約します。
2. 優先されるようにグローバル PR を変更します。
   - マルチリード開始時のコンセンサス。
   -limb-lead 生の PR コア。
   - 代表テンプレート PR。
3. 長い PR/低振幅 P の場合、中央値の代表テンプレートを使用して P 開始を再テストします。
4. PR セグメント/ベースライン 単一ビートのローカル PR セグメントだけに依存しないでください。同じリードの拍動を表す PR セグメントの中央値を以前のベースラインとして使用できます。

<a id="32-qrs-波群"></a>
## 3.2 QRS ウェーブ グループ

現在の実践:

- 各リード×ビートは、QRS オンセット/オフセット、Q/R/S、R'/S'、ノッチ、スラー、VAT、QRS エリアを個別に検出します。
- representative beat は、シングルショットのローカル修正を支援する前に、グループ レベルの境界を構築するために最初に使用されます。
- `_apply_multilead_consensus()` は、マルチリード QRS オンセット/オフセットを使用して、`qrs_consensus_ms` および `qrs_wide_ms` を取得します。
- グローバル QRS はコンセンサスを最初に使用し、生のコア フォールバックを備えています。

利点:

- QRS は現在、マルチリードのコンセンサスを最も活用している部分です。
- リードごとの WaveBound はコンセンサスによってカバーされず、リードの形態学的差異は保持されます。
- 後期端末 QRS には、すべての ST/T テールが QRS として扱われることを避けるために、分類専用/測定シャントがあります。

レコード 5 によって明らかになった問題:

- グローバル QRS = 112 ミリ秒、GT = 80 ミリ秒、誤差 +32 ミリ秒。
- リードごとに独立した QRS 違いは非常に大きいです。
  - I: 70 ミリ秒
  - II: 80ミリ秒
  - III: 191 ミリ秒
  - aVF：128ミリ秒
  - V1: 66 ミリ秒
  - V5: 82 ミリ秒
- `qrs_consensus_ms = 112 ms`、`qrs_wide_ms = 128 ms`。

これは、現在のコンセンサスが確かに III の 191 ミリ秒の極端な値を抑制していることを示していますが、それはまだいくつかの後期オフセットによって拡大されており、グローバル QRS の幅が広くなっていることがわかります。

短所:

- QRS コンセンサスは遅延オフセットに対して十分に堅牢ではありません。
- 代表的なテンプレートは、「標準 QRS エンドポイント」コンセンサスに対する強力な制約として機能しません。
- QRS オフセット エラーは ST-J、JT、QT パスに渡されます。

提案:

1. QRS グローバル測定では、第三者証拠として `representative_median_template_qrs` を追加する必要があります。
2. リードごとの生の QRS コアが 70 ～ 90 ms で、コンセンサスが 110 ms を超える場合、遅延オフセットには少なくともマルチリードの形態学的証拠が必要です。
3. QRS オフセット コンセンサスは次を出力する必要があります。
   - 測定オフセット
   - 分類/ワイドオフセット
   - 生のコアオフセット
   -テンプレートオフセット
4. ST-J/ST40/ST80 は測定オフセットに基づく必要があります。 BBB/IVCD 分類は、分類オフセットに基づいて行うことができます。

<a id="qrs-offset-raw-repair-update"></a>
### QRS オフセット未加工修復アップデート

QRS オフセット生修理パスが現在追加されています。各ビートの信頼できる QRS リードの測定端末コンセンサスを使用して、明らかに遅い/早い、信頼性の低い生の `qrs.offset` 外れ値を特定し、すべてのリードを強制的に同じオフセットに引っ張ることなく、測定エラーと判断されたリード×ビートのみを修復します。

修正後、`LeadBeatFeatures.qrs.offset` が書き戻され、再計算されます。 `qrs_ms`、`qrs_area`、`qrs_signed_area`、`j_index`、`st_on_mv`、`st_mid_mv`、`st_80ms_mv`、`jt_ms`、`qt_ms`、および安全に再計算できるターミナル QRS 形態フィールド。幅広い QRS 分類は `qrs_wide_ms` パスを保持しており、測定オフセットと混合されません。

適切な QRS を過度に短くすることを避けるために、修復ゲートは、元の幅が適切であり、ST/T の混乱やビートの信頼性が低いという証拠がないリード×ビートも保護します。コンセンサスフィードバックによって修正できるのは、明らかなロングテール、信頼性の低い、または信頼性の低いコンテキストのみです。

LUDB フルバッチの結果:

- QRS MAE: 9.88 -> 9.88
- QRS バイアス: 5.727 -> 5.727
- `|QRS diff| > 20 ms` / `> 40 ms`: 17/2 -> 17/2
- QT MAE: 13.4625 -> 13.4625
- QRS/P/T が欠落しています: 0/2669/258 -> 0/2669/258
- raw QRS 任意の境界がありません: 0 / 25860
- `qrs_offset_repaired_by_consensus`: 6 レコードにわたる 7 行

<a id="33-st-segment-j-point"></a>
## 3.3 STセグメント/Jポイント

現在の実践:

- ST-J、ST40、ST80はリード×ビートごとに測定されます。
- 代表リードの `st_on_mv` は `_representative_st_j_params()` によって集計されます。
- QRS テールガードが見つかった場合、ST-J の信頼性が低いとマークされます。
- 12SL プロファイルには STJ/STM/STE もあります。
- QRS オフセット未加工修復後、ST/J 未加工再測定パスを追加します。`st_j_unreliable` の証拠があるリード×ビート、テール ジャンプ、J オフセット外れ値、または信頼性の低いビートの場合、同じビート内の信頼できる QRS リードの J ポイント コンセンサスを使用して、元のリード波形で ST-J/ST40/ST80 を再サンプリングします。

利点:

- ST はリードごとの機能であり、単に世界的なコンセンサスによってカバーされるものではありません。
- QRS テールガードがあり、一部の QRS 端による ST の汚染を防ぎます。
- ST/J 生再測定は、`qrs.onset`、`qrs.offset`、または互換性のある `j_index` を変更せず、実際の ST サンプル アンカーを `st_j_remeasured_index` に書き込み、ST 値を再計算するだけなので、実際のリード間 QRS の差は保存できます。

短所:

- 生の再測定をトリガーしない ST-J は、依然として、代表テンプレートの J ポイントではなく、リードごとのローカル QRS オフセットに主に基づいています。
- `_apply_multilead_consensus()` は、`qrs_wide_ms` が ST-J/ST40/ST80 と競合する場合にのみ、ST-J を信頼性の低いものに設定します。実際の再測定は、以前の ST/J 生再測定パスで行われます。
- representative beat ST セグメントの使用は十分に安定していません。ST-J は rep_feature を使用することもあれば、プールされた中央値を使用することもありますが、コンセンサス J ポイント リサンプリングを明示的に使用しません。

<a id="stj-raw-remeasurement-update"></a>
### ST/J 生の再測定の更新

現在、新しい ST/J raw 再測定パスが追加されています。 QRS オフセット生修復後、サンプリング アンカーと同じビート内の信頼できる QRS リードの J ポイント コンセンサスを使用し、`st_j_unreliable`、テール ジャンプ、オフセット外れ値、またはビートの信頼性の低い証拠を使用してリード×ビート ST セグメントのみを再テストします。

このパスは、`qrs.onset`、`qrs.offset`、または互換性のある `j_index` を変更しませんが、ST サンプル アンカーを `st_j_remeasured_index` に記録します。修正により、`st_on_mv`、`st_mid_mv`、`st_80ms_mv`、`st_slope_mv_per_ms`、および `st_morphology` が再計算されます。すでに J/ST40/ST80 が一致している場合、真の ST 上昇/下降は平滑化されません。

LUDB フルバッチの結果:

- PR MAE: 9.5372 -> 9.5372; QRS MAE: 9.8800 -> 9.8800; QT MAE: 12.8575 -> 12.8575
- PR/QRS/QT `|diff| > 20 ms`: 17/17/33 -> 17/17/33
- QRS/P/T がありません: 0/2669/258 -> 0/2669/258
- `st_j_unreliable`: 305
- `st_j_remeasured_by_consensus`: 164 レコードにわたる 1724 行
- 分割理由: `offset_outlier=1092`、`tail_guard=417`、`beat_unreliable=215`

レコード 5:

- 私は代表的な ST-J = -0.104 mV をリードしますが、プールされた ST-J 中央値は約 -0.069 mV です。
- aVL 代表 ST-J = +0.042 mV ですが、プールされた ST-J 中央値は約 -0.061 mV です。

これは、単一ビートを表す ST レベルがプールされたビートと一致しない可能性があることを意味します。代表的な波形が medoid シングルビートである場合、この ST-J の差は、安定した ST セグメントではなく、シングルビートのベースライン/オフセットに由来する可能性があります。

提案:

1. ST セグメントの独立した代表テンプレート測定を確立します。
   - `st_j_raw_local`
   - `st_j_consensus_j`
   - `st_j_template`
   - `st_j_12sl`
2. 診断/レポートには、単一の medoid ST-J ではなく、`st_j_template_consensus_j` または信頼性の高いプール中央値が推奨されます。
3. 代表的な ST-J とプール中央値の差が >0.05 ～ 0.08 mV である場合、不安定としてマークされるか、プール中央値にフォールバックする必要があります。
4. ST セグメントは、ワイド/分類オフセットではなく、QRS 測定オフセットにバインドされる必要があります。

<a id="34-t-波与-qt"></a>
## 3.4 T波とQT

現在の実践:

・リード×ビートごとにTピーク/Tエンドを独立して検出。
- T 候補の選択では、極性、面積、幅、ST-T の混乱が考慮されます。
- マルチリードコンセンサスでは、信頼できる QT リードの T エンド中央値を使用して、`qt_consensus_ms` を取得します。
- 独立系 `qt_ms` とコンセンサス `qt_consensus_ms` が代表リードとして維持されます。
- グローバル QT は信頼できるリードの中央値を優先し、`consensus_vs_independent_per_lead` を記録します。

利点:

- QT は現在、QRS を除き、マルチリード コンセンサスを最大限に活用する機能です。
- III 独立 QT = 504 ミリ秒、レコード 5 の V1 = 328 ミリ秒。グローバル QT はコンセンサス使用後 402 ミリ秒であり、単一リードの極値によって直接引きずられることはありません。
- `global_qt` メタデータは、監査を容易にするために、リードごとに独立した QT とコンセンサス QT を保持します。

短所:

- T 波形、T 振幅、T 面積は、依然として representative beat から取得されるか、未加工でプールされたものである可能性があり、必ずしもコンセンサス T エンドを使用して再統合されるとは限りません。
- `qt_consensus_ms` はグローバル QT で高い優先順位を持ちますが、おそらく真のリードの差が犠牲になります。
- 低サポート/レスキュー パスのエラーは、メイン パスよりも大幅に大きくなります。

レコード 5:

- グローバル QT = 402 ミリ秒、GT = 382.5 ミリ秒、誤差 +19.5 ミリ秒。
- 独立した QT:
  - V1: 328ミリ秒
  - V2/V3: 368 ミリ秒
  - I/II/V5: 384 ミリ秒
  - aVF：416ミリ秒
  - III: 504 ミリ秒
- コンセンサス QT = 402 ミリ秒。

これは、コンセンサスによって外れ値が抑制されているものの、全体的な T 終了または QRS の開始がまだわずかに遅い/長いことを示しています。

提案:

1. T 形態を区別する必要があります。
   -生のローカル T 境界
   - コンセンサスTエンド
   - 代表テンプレートの T 境界
2. T 面積/T 持続時間/Tpe を診断に使用する場合、代表テンプレートのコンセンサス T-end に従って再計算する必要があります。
3. `st_t_confusion` のリードは、代表波形と隣接するリードが満場一致でサポートされない限り、T 形態マスター テーブルに直接参加すべきではありません。
4. グローバル QT は引き続きコンセンサスを優先できますが、レポートには独立 QT とコンセンサス QT の両方を表示する必要があります。

<a id="t-end-raw-repair-update"></a>
### T エンド RAW 修復アップデート

現在、新しい T エンド raw リペア パスが追加されています。各心拍における信頼できる QT リードの T エンド測定コンセンサスを使用して、明らかに初期/後期であり、信頼性やリスクの証拠が低い生の `t.offset` 外れ値を特定します。測定誤差があると判断されたリード×ビートのみを修復するものであり、すべてのリードを同じT端に強制するものではありません。

修正後、`LeadBeatFeatures.t.offset`が書き戻され、`qt_ms`、`jt_ms`、`t_dur_ms`、`t_area`、`t_signed_area`、`tpe_ms`が再計算されます。高い信頼性と合理的なフォームを備えた本物のロンTは、強制的にコンセンサスに引き戻されることはありません。修理候補が QT `<280 ms` を引き起こす場合、QRS テール/ST-T が誤って T 端とみなされる混乱を避けるために、修理は拒否されます。

consensus raw repair の前処理として、現在、より保守的な T-end dual-method raw rescue pass が新たに追加されています。このパスは「明らかに早期に切断された、低信頼度の、またはフォールバック/リスクのある」raw `t.offset` だけを処理し、まず信頼性の高い QT leads を用いてビートレベルの T-end consensus を確立し、次に同一導聯の生波形上で chord、slope-return、tangent の3つの T offset 証拠を同時に計算します。3つの端点の spread `<=30 ms` が、候補が次の QRS を跨がない、QT `<280 ms` を引き起こさない、かつ延長が `160 ms` を超えない場合に限り、raw `t.offset` を書き戻します。

このパスの目的は最終レポートの集計精度を向上させることではなく、生データ `lead × beat` の T offset そのものの信頼性を高めることです。後続の consensus repair provenance と混同しないよう、`t_offset_dual_original_index`、`t_offset_dual_rescued_index`、`t_offset_dual_delta_ms`、`t_offset_dual_consensus_index`、`t_offset_dual_support`、`t_offset_dual_used_leads`、`t_offset_dual_chord_index`、`t_offset_dual_slope_index`、`t_offset_dual_tangent_index` および `t_offset_dual_method_spread_ms` を個別に記録します。

LUDB full-batch 結果：

- QT MAE: 13.4625 -> 12.8575
- QT bias: -1.1875 -> -1.2125
- `|QT diff| > 20 ms` / `> 40 ms`: 34/17 -> 33/14
- QRS MAE: 9.88 -> 9.88
- PR MAE: 9.537236842105264 -> 9.537236842105264
- QRS/P/T missing: 0/2669/258 -> 0/2669/258
- raw T peak/offset missing: 378 / 25860
- `t_offset_dual_method_rescued`: 1 row across 1 record
- dual rescue case: record 54, lead V1, beat 5, `3522 -> 3534` samples (`+24 ms`), support 8, method spread `28 ms`
- `t_offset_repaired_by_consensus`: 1201 rows across 167 records
- consensus repair reason split: 1001 `late_outlier`, 200 `early_truncation`

## 3.5 U 波

現在の手法：

- U 波は主に T-end 後の二次ピークフラグとして扱われる。
- 顕著な U 波は T-U nadir および T-end clamp に影響を与える。
- 独立した U onset/peak/offset の代表波形測定は存在しない。

課題：

- 導聯ごと/ビートごとの U 波特徴量パイプラインが完全ではない。
- 代表的な U 波の形態（morphology）がない。
- 顕著な U 波が QT/T-end に与える影響はマークできるが、解釈可能性が不十分である。

提案：

1. U 波を体系的に利用するには、`u` bounds および `u_amp_mv/u_area/u_confidence` を新たに追加すべきである。
2. QT と QU は別々に出力すべきである：`qt_ms`、`qu_ms`。
3. T-end が U 波によって修正された場合、メタデータに元の T-end と T-U nadir を保持する。

<a id="36-qt-dispersion"></a>
## 3.6 QT 分散（dispersion）

現在の手法：

- `_raw_qt_dispersion()` は consensus QT ではなく、代表導聯の独立した `qt_ms` を使用する。
- ただし、低信頼度、高い標準偏差（SD）、見えない T 波、経路が不合理な導聯はフィルタリングされる。
- 生データの分散が大きすぎる場合、コアクラスターを選択し、コア導聯クラスターの最大値と最小値の差を返す。

レコード 5 において：

- アルゴリズムによる QT 分散 = 22 ms。
- 正解（GT）QT 分散 = 64 ms。
- 独立した QT 値には実際には顕著な差がある：V1 328 ms、III 504 ms、aVF 416 ms。
- 現在のロジックはこれらの外側の値をフィルタリング/クラスターリングしてコアクラスターのみを保持するため、分散は 22 ms に圧縮される。

結論：

- 現在、分散を計算するために consensus QT を完全に誤って使用しているわけではないが、「コアクラスター」戦略は臨床的に意味のある導聯間の分散を体系的に過小評価する。

提案：

1. 以下の両方を出力する：
   - `qt_dispersion_raw_all_reliable`
   - `qt_dispersion_core_cluster`
   - `qt_dispersion_reported`
2. LUDB GT と比較する際、アノテーション定義により近い生データの独立導聯分散を優先する。
3. レポートではコア分散のみを表示せず、そうしないと導聯間の差異が隠れてしまう。

<a id="37-axis"></a>
## 3.7 軸（Axis）

現在の手法：

- P/QRS/T 軸は、代表導聯の符号付き面積または正味振幅から計算される。
- 信頼度を重みまたはフィルタリングに使用する。

利点：

- 軸は本質的に導聯間の組み合わせを必要とし、現在では単一導聯にのみ依存していない。
- 単一点のピークよりも符号付き面積の方が安定している。

課題：

- 代表導聯の P/T 面積がメドイド（medoid）の単一ビートに由来する場合、ノイズや ST ベースラインが軸に影響を与える。
- T 軸の欠損が多く、T 振幅/信頼度のゲートリングが保守的であることを示している。
- 比較において軸の差分に円距離（circular distance）が使用されていないため、一部の誤差が増幅される。

提案：

1. 軸には、メドイドの単一ビートではなく、中央値代表テンプレートの符号付き面積を使用する。
2. T 軸に対して、信頼度と使用された導聯を出力する。
3. 比較には円差分（circular difference）を使用する。

<a id="4-report-comparison-的混用问题"></a>
## 4. レポート/比較における混用問題

現在の `compare_annotations.py` では、導聯ごとの QRS/QT 比較において consensus が優先される：

- `qrs_ms -> qrs_consensus_ms`
- `qt_ms -> qt_consensus_ms`

これにより、`*_comparison.txt` の導聯ごとの QRS/QT が12導聯すべてで完全に同一に見えるようになる。

レコード 5 において：

- アルゴリズムレポートの導聯別表は生データの代表値を表示している：
  - I QRS 70, II QRS 80, III QRS 191, aVF QRS 128
  - I QT 384, III QT 504, V1 QT 328
- 比較表では、すべての導聯で QRS = 112、QT = 402 と表示されている。

したがって、比較のリードごとの QRS/QT は、純粋なリードごとの代表的な測定値ではなく、コンセンサス測定値です。この口径は以下をマスクします:

- どのリードが独立して測定が不十分であるか。
・代表波形がリードを改善するかどうか。
- リードの差を過度に平坦化するかどうかのコンセンサス。

比較/レポートを変更することをお勧めします。

1. リードごとの比較におけるカラムの内訳:
   - `raw_independent`
   - `representative_template`
   - `pooled_median`
   - `consensus`
2. グローバル QRS/QT のコンセンサスを要約して使用します。
3. リードごとのテーブルでは、デフォルトで raw の代わりにコンセンサスを使用しないでください。
4. QT 分散の場合、生クラスターとコアクラスターのどちらを使用するかを指定してください。

qt_ms_raw_lead

qt_ms_consensus_beat
qt_ms_global_reported

st_j_raw_local

<a id="8-对-record-5-的具体判断"></a>
## ８．記録５に対する具体的な判決

レコード 5 は、現在のプロセスが有用ではあるが十分ではないことを示しています。

- HR および PR は許容可能です: HR エラー -0.2 bpm、PR エラー -8 ms。
- QRS の方が幅が広い: グローバル QRS 112 ミリ秒対 GT 80 ミリ秒。これは、QRS コンセンサスが遅延オフセットによって広がっていることを示しています。
- QT が長くなります: グローバル QT 402 ミリ秒対 GT 382.5 ミリ秒。一部は QRS/グローバル基準バイアスによるものです。
- QT 分散の過小評価: コア クラスター フィルタリングによる 22 ミリ秒対 GT 64 ミリ秒。
- ST-J の一部の誘導における代表中央値とプール中央値の差は明らかであり、中央値の単一拍が必ずしも ST セグメントに適しているわけではないことを示しています。

したがって、レコード 5 の改善の焦点は「代表/コンセンサスがあるかどうか」ではなく、次の点にあります。

1. QRS ターミナルのコンセンサスは、生/テンプレート コアによってさらに制約される必要があります。
2. ST セグメントは、代表的な中央値テンプレート + コンセンサス J ポイントを使用して再テストする必要があります。
3. QT 分散は独立したリード値で再定義する必要があります。
4. 比較表では、デフォルトでリードごとの QRS/QT をコンセンサスに置き換えることを停止する必要があります。
