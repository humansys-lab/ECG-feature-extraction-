# エージェントの改訂サイクル（改訂）問題の分析と改善リスト

分析日: 2026-08-01
解析対象：`ecgagent/agent/loop.py`の確定的検証・修正サイクル
証拠のソース: `ptbxl_09000_medgemma27b_v16/09000_hr` (プロトコル v16、MedGemma-27B)、
`ptbxl_09000_qwen36_27b/09001_hr` (プロトコル v14、Qwen3.6-27B)、およびすべて
1138 件の既存の判決に関する要約統計。

---

<a id="0-结论摘要"></a>
## 0. 結論の概要

修正サイクルは 3 ラウンド以内に収束するか、ほとんど収束しません。 4ラウンド以上継続して、
ゲインは非常に低いですが、レコード全体の実時間の 40% 以上を消費します。

|リビジョンに入るラウンド数 |レコード数 |最終検証済み |説明 |
|---|---:|---:|---|
|ラウンド 1 ～ 3 | 372 | **363 (97.6%)** |ここでは改訂メカニズムが効果的であり、弱体化すべきではありません。
| ≥4 ラウンド (トップ) | 239 | **47 (19.7%)** |頂点に達した後の回復は基本的に不可能です |

上位にランクインした 239 アイテムの中には、次のようなものがあります。

|エンディング |行数 |割合 |
|---|---:|---:|
|レポートを出力しましたが、証拠の検証に失敗しました (`ok=True`、エラーなし) | 136 | 56.9% |
|予算は使い果たされたが、契約はまだ通過していない | 99 | 41.4% |
|リビジョンは JSON に変更されました。 4 | 1.7% |

> サマリーキャリバーの説明: 統計では、**リビジョンに入る前に失敗した** レコードが除外されます (合成出力は解析できません。
> API 402/400 など)、このカテゴリには 527 のエントリがあり、改訂サイクルとは関係ありません。以前のバージョンの統計にはそれらが混在しています。
> `revisions=0` はベースラインを大幅に抑制します。

**核心的な判断: 問題は「修正ラウンドが足りない」ことではなく、最初のフィードバックの質です。 **
予算を 4 から 6 に増やしても効果はありません。ラウンド 1 のフィードバックを実用的なものにします。

## 1. 2 つのケースのラウンドごとの解剖学

<a id="11-medgemma-09000hr-三轮输出逐字节相同"></a>
### 1.1 MedGemma / 09000_hr ——3 ラウンドの出力はバイトごとに同じです

フェーズのタイムライン (改訂部分):

|ラウンド |モデルラウンド |ツール呼び出しの成功 |経過時間 |停止理由 |
|---|---:|---:|---:|---|
|修正 1 | 3 | 1 | 280.32秒 |エンドターン |
|修正 2 | 1 | 0 | 141.84秒 |エンドターン |
|改訂 3 | 1 | 0 | 142.46秒 |エンドターン |

修正時間は合計 564.6 秒で、記録全体の 1404.88 秒の **40.2%** を占めました。

3 ラウンドの出力を md5 比較します。

```
synthesize   md5=d1d5271450c5
revise 1     md5=e9f7725d0113   ← 有变化
revise 2     md5=e9f7725d0113   ← 与上一轮完全相同
revise 3     md5=e9f7725d0113   ← 与上一轮完全相同
```

最終的には「契約改訂が停止しました: モデルは変更されていない無効な値を返しました」という結果になりました。
評決は二度失敗した。

**改訂 1 の変更自体にも問題があります。 ** 合成ステージの出力
`nonspecific_ivcd`、理由は「QRS の制限時間 80 ミリ秒は正常範囲内 (<120 ミリ秒)」です—
それを自分で証明してください。 IVCD ガードは正しくインターセプトします。モデルを変更する方法は、`nonspecific_ivcd` を削除し、次のように置き換えることです。
`st_depression`、その理由は、「ST セグメントはほとんどのリードで水平であり、**通常の変動と一致している**」ためです。
同じタイプの自己否認エラーですが、診断コードが異なります。 `st_depression`はガードがないのでパス。

モデルはガードの背後にある**エラー クラス**を理解せず、部分的な置換のみを行います。

この記録を複製するための契約事項 (5 項目):

```
1. `summary` 含未落地数量 (191 ms, 80 ms, 497 ms)
2. ranked_complete_interpretations[0].complete_diagnosis 含未落地数量 (同上)
3. ranked_complete_interpretations[1].complete_diagnosis 含未落地数量 (同上)
4. diagnoses[2].reasoning 含未落地数量 (100 bpm)
5. interval_measurement_contexts[0].residual_evidence 未引用任何 T/U 分量波观察
```

第 4 条 **不満**: 原文は「心拍数は 100 bpm より 113 bpm 高く、頻脈の定義を満たしています。」です。
ここで、100 bpm は **診断定義の閾値** であり、患者の測定値ではありません。検証に合格するには、定義を削除することしかできません。
または、`value=100`の証拠品を偽造すること（後者は他のルールで禁止されています）。モデルはどちらの道も選択しませんでした。
なのでそのまま再投稿。

同時に、記事 1 ～ 3 にも構造的な問題があります。PR 191 ミリ秒 / QRS 80 ミリ秒はすべて **正常値**です。
唯一の着陸メカニズムは `diagnoses[].evidence` であり、これは陽性所見の場合にのみ存在します。
現在のスキーマには通常の測定の余地はありません。

<a id="12-qwen-09001hr-四轮修订只改了一个字符"></a>
### 1.2 Qwen / 09001_hr —— 4 回の改訂で変更されたのは 1 文字のみ

|修正 2 | 4 | 3 | 0 | 103.48秒 |エンドターン |
|改訂 3 | 7 | 3 | 7 | 123.37秒 |エンドターン |
|改訂 4 | 7 | 3 | 5 | 118.54秒 |エンドターン |

合計リビジョンは 379.5 秒で、863.43 秒全体の **44.0%** を占めました。

```

revise 1     len=3     md5=27c4e28d48   ← 输出只有 3 个字符，turn_limit
```

```diff

```

キャラクター。最上位キーの欠落など、12 件の検証問題のうち 1 つが解決されていません。
`ranked_complete_interpretations`、`normal_ecg`、`left_atrial_abnormality`
相互に排他的、不十分な LAA 証拠しきい値、7 つの根拠のない数量、1 つの算術矛盾。

同じ実行の別のレコード `09000_hr` はさらに悪いです。

<a id="2-根因"></a>
## 2. 根本原因

<a id="r1-反馈是一次性平铺的问题清单没有优先级也没有可执行修法"></a>
### R1。フィードバックは 1 回限りの問題のフラットなリストであり、優先順位や実行可能な修正はありません。

[`loop.py:589-602`](../ecgagent/agent/loop.py#L589-L602)、非判定モード
`_contract_feedback` が行うことは 2 つだけです。最大 16 個の質問を箇条書きにまとめます。
もう 1 つの一般的なヒント。

```python
lines = [
    "The verdict violates the deterministic output contract. Fix every item:",
    *[f"- {problem}" for problem in structural[:16]],
]
```

モデルは、以下を含む 12 個の並列リクエストを受信しました。

- **機械式** (説明内の数字を削除)
- **構造クラス** (欠落している最上位キーを埋めます)
- **実質** (しきい値を満たさない診断を削除します)
- **満足できないクラス** (定義されたしきい値を患者の測定値として使用して実装します)

それらを区別する信号はありません。 「あらゆる項目を解決してください」 達成不可能な要求に直面したとき、
最も安価な戦略は何も変更しないことです。どちらの場合でも動作はまったく同じです。

<a id="r2-不可满足的问题会毒化整批修订"></a>
### R2。満足のいかない問題があると、リビジョン全体が損なわれてしまいます。

リストに解決できない項目が 1 つある限り、モデルは修正可能な 11 項目を修正するのではなく、12 項目すべてを放棄する傾向があります。
現在のループには「部分修復」の概念がありません。`structural` は空であるか、失敗しています。

2 つの満たされない/誤検知ルールが確認されました。

- [`diagnostic_prompts.py:466-505`](../ecgagent/agent/diagnostic_prompts.py#L466-L505)
  `_reject_quantities` **しきい値の定義** の誤検知。インターバル書き込みのみを免除します
  (`60-100 bpm` は合格)、単一のしきい値は免除されません (`高于100 bpm` はブロックされます)。
- [`semantic_guard.py:21-31`](../ecgagent/agent/semantic_guard.py#L21-L31)
  `_COMPARISON_RE` の否定の盲点は、正しい「しきい値に達していない」ことを算術矛盾として扱います。
  詳細については、§5 の別のエントリを参照してください。

<a id="r3-修订预算是全局共享的一次解析失败就吃掉-14"></a>
### R3。修正予算はグローバルに共有され、解析失敗が発生すると 1/4 が消費されます。

[`loop.py:1200`](../ecgagent/agent/loop.py#L1200)、`_request_revision` 内部
`while result.revisions < self.max_revisions` は同じ構造/証拠リビジョンを共有します**
カウンタ**、デフォルトは `max_revisions = 4` ([`loop.py:353`](../ecgagent/agent/loop.py#L353))。

Qwen の場合、リビジョン 1 は JSON 以外の 3 文字を返します。これにより、予算が 1 回直接消費されます。
実質的な修理はあと3回だけ残っています。純粋なフォーマット事故などの解析失敗は、セマンティック リビジョン クォータと競合すべきではありません。

<a id="r4-修订阶段允许工具调用模型会把回合花在工具上而不是改文本"></a>
### R4。リビジョンフェーズではツール呼び出しが可能で、モデルはテキストを変更するのではなくツールにターンを費やします。

Qwen の改訂 1: 7 ラウンド、3 回のコール成功、**11 回のコール拒否**、バンプ
`turn_limit` の後には 3 文字のみが出力されます。モデルは、改訂フェーズ中にツール呼び出しの再試行ループに陥ってしまいます。
JSON を編集するところまではまったく至りませんでした。

ほとんどの契約書の問題 (番号の削除、キーの入力、診断の解除) **新しい証拠は必要ありません**。純粋にテキスト編集です。
ただし、現在の設計では、リビジョン フィードバックとともに完全なツールセットがモデルに渡されます。

<a id="r5-停机判据滞后触顶前会白烧两轮"></a>
### R5。シャットダウン基準が遅れており、頂上に到達するまでに 2 ラウンドが無駄になってしまいます。

[`loop.py:475-492`](../ecgagent/agent/loop.py#L475-L492) のストール検出要件
連続する 2 ラウンドで署名がまったく同じである場合にのみ停止します。つまり、最初の再送信は停止しません。
2 回目の停止まで待つ必要があります。MedGemma ケースは 142 秒間無駄に燃えま​​した。

そして [`loop.py:452-458`](../ecgagent/agent/loop.py#L452-L458) の `max_revisions`
** の次のラウンドを要求する前に ** が発生すると判断されるため、2 つのシャットダウン パスが互いに競合します。Qwen ケースが最初に衝突します。
`max_revisions` レポート `failed deterministic contract validation`、
MedGemma ケースが最初に停止し、`revision stalled` を報告しました。 「機種変更ができない」という現象も同様ですが、
2 つの異なるエラー メッセージが生成され、後続の統計とトラブルシューティングにノイズが追加されます。

<a id="r6-全有全无实质正确的报告被整条丢弃"></a>
### R6。実質的に正しいレポートは、まったくもって完全に破棄されます。

Qwen/09001 の報告は、実際、臨床的に非常に優れています。洞調律を正確に決定し、正しく特定され、拒否されました。
心房細動検出器には偽陽性があり、T 軸を正しくラベル付けする信頼性には疑問があります。唯一の重大な誤りは、1 つを過剰に報告したことだった。
左心房の異常。しかし、契約が通過しなかったため、記録全体が `failed` と判定され、レポートの先頭にマークが付けられました。
「証拠と意味の検証: 実行されていないか、ステータスが不明です。」

ピーク記録の 136 (56.9%) は実際にレポートを作成しましたが、検証に失敗しました - 現在
「実質的に使用可能だが完全には準拠していない」と「完全な障害」を区別するメカニズムはありません。

<a id="r7-被拒工具调用完全不可观测"></a>
### R7。拒否されたツール呼び出しは完全に観察できません

[`trace.py:77`](../ecgagent/trace.py#L77) は、`rejected_calls` の **カウント** のみを記録します。
ツール名、パラメータ、拒否理由は記録されません。 Qwen/09001 はプロセス全体で 27 回拒否されました。
トラブルシューティング時は完全にブラックボックス。これが、1,325,708 個のプロンプト トークンを焼き付けた理由です
(MedGemma 同様のタスク 566,952)。

<a id="3-改进建议按性价比排序"></a>
## 3. 改善提案（費用対効果の順に並べ替え）

<a id="p1-反馈分层下发机械类问题直接给替换文本"></a>
### P1 — フィードバックはレイヤーに分散され、機械的な問題はテキストに直接置き換えられます。

`_contract_feedback` を変更し、修復の難易度ごとにグループ化し、機械的な問題に対して **正確な修正アクション** を提供します。

```
必须修复（结构）：
- 缺失顶层键 `ranked_complete_interpretations`，补一个数组
- `normal_ecg` 与 `left_atrial_abnormality` 互斥，二选一

必须修复（证据门槛）：
- diagnoses[1] `left_atrial_abnormality` 证据不足，移入 differential_diagnoses

机械修改（无需调用工具，直接改文本）：
- `summary` 删除 "92ms"、"434ms" 两处数字，或把它们加进已引用的证据项
- diagnoses[1].evidence[0].claim 拆成两条，每条只写一个数量
```

このパッケージにより、バリデーターは `severity` フィールドと `mechanical: bool` フィールドを各質問に取り込むことができます。
現在のプレーン文字列の代わりに。これはこのリストで最も収益性の高いアイテムです -
ラウンド 1 ～ 3 の収束率はすでに 97.6% です。さらに多くのレコードをこの範囲に押し込むだけです。

<a id="p2-修订阶段默认关闭工具按需再开"></a>
### P2 — ツールは改訂フェーズ中はデフォルトで閉じられ、必要に応じて再度開きます。

契約問題の大部分は純粋なテキスト編集です。提案:

- 最初の改訂ラウンドでは **ツールは提供されません**。フィードバックと現在の判定のみが提供され、完全な返品が必要です (JSON)
- フィードバックに「測定値を再読み取りする必要がある」タイプの問題が含まれている場合のみ (例:
  `[diagnosis_evidence_gate]`、値が一致しません)、ツールは 2 番目のラウンドで開かれます

R4 を直接排除し、トークンの消費を大幅に削減します。

<a id="p3-拆分修订预算"></a>
### P3 — 分割修正予算

`max_revisions` を 2 つの独立したクォータに分割します。

- `max_format_retries` (解析が失敗した場合は再試行、推奨事項 2)
- `max_semantic_revisions` (大幅な改訂、推奨事項 3)

解析インシデントがセマンティック リビジョン クレジット (R3) を侵食しなくなりました。また、セマンティック リビジョンの制限も 4 から 3 に引き下げられました -
データによると、ラウンド 4 ではゲインがほとんどなく、カットオフによりトップ記録ごとに約 120 秒を節約できます。

<a id="p4-统一并提前停机判据"></a>
### P4 — シャットダウン基準の統一と高度化

- ストール検出が**1ラウンド**に変更され、変化がない場合は停止します(現在は2ラウンド必要です)。`max_revisions`
  トップとストールは同じエラー コードにマージされ、「未修正の問題リストの最終ラウンド」が表示されます。
- シャットダウン中に未修正の問題を `result.verification` に書き込むと、トラックに表示されなくなります。
  「確定的な検証報告書はない」というギャップがあり、現時点では両事件の足跡は見つからない。検証者は具体的に何と言ったのですか？

<a id="p5-引入部分通过状态"></a>
### P5 — 「部分パス」ステータスの紹介

`ok` / `verified` に加えて `contract_incomplete` を追加: 契約は完全には通過していませんが、
評決の構造が完成し、実質的な矛盾がない場合は、レポートを保管し、**特定**の不合格項目をレポートの先頭にリストします。
一般的な「未実行またはステータス不明」ではなく。 R6の136項目に対応します。

<a id="p6-轨迹记录被拒调用明细"></a>
### P6 — 拒否された通話の詳細の記録

ツール名、パラメータの概要、および拒否された各呼び出しの拒否理由を `trace.py` に記録します。
数行のコードですが、現在の 27 件の失敗した呼び出しは完全に検出できません (R7)。

<a id="p7-修掉两条会误伤正确推理的校验规则"></a>
### P7 — 正しい推論を損なう可能性のある 2 つの検証ルールを削除します。

これら 2 つの項目は解決不可能なフィードバックを作成し、R2 を直接トリガーします。

1. `_reject_quantities` 定義されたしきい値を解放します - ガイド定数ホワイトリストを追加します
   (60/100/120/200 bpm、120 ms、200 ms、440/460/500 ms など)、
   または、チェックを `summary` / `complete_diagnosis` などの説明フィールドに限定します。
   `reasoning` には影響しなくなりました
2. `_arithmetic_problems` の否定ブラインド領域 - §5 を参照

<a id="4-验证方式"></a>
## 4. 検証方法

変更後は、次のことが確認できるはずです。

- ピーキング（4 ラウンド以上）記録の割合は 21.0% (239/1138) から減少しました。
- 改訂に入る記録の全体的な検証率は 67.1% から増加しました
- 同じmd5を2ラウンド連続で出力する状況がなくなる(`trace`にアサーションを追加可能)
- 修正段階の`rejected_calls`の総数が大幅に減少（P2の直接効果）

回帰サンプルは次の 2 つの項目で修正されています。

|ロギング |期待される動作 |

<a id="5-附算术守卫的-negation-盲区"></a>
## 5. アタッチメント: 算術ガードの否定ブラインドエリア

修正ループとは関係ありませんが、答えられないフィードバックが生成されるため、R2 を直接悪化させます。これにも注意してください。

[`semantic_guard.py`](../ecgagent/agent/semantic_guard.py)
`_arithmetic_problems()` 否定文を算術矛盾として正しいと判断します。最小再発:

```
FLAG  V1导联P波终末力约为0.0039 mV*s，未达到左房异常的经典阈值（>0.04 mV*s）
        → "0.0039 > 0.04 is false"          【句子本身完全正确】
FLAG  QRS时限92 ms，未超过120 ms
        → "92 超过 120 is false"             【句子本身完全正确】
ok    PTF为0.0039 mV*s，低于0.04 mV*s的阈值
ok    心率62 bpm，未达到100 bpm的心动过速标准
```

2 つの独立した欠陥:

1. **否定の盲点。 ** `_COMPARISON_RE` の `context` グループ
   `[^\d]{0,48}?` は 2 つの数字の間の否定的な単語を丸ごと飲み込みます。
   `_arithmetic_problems` は `_NEGATION_RE` を呼び出すことはありません (この正規表現は
   `_positive_narrative_match` を使用します)。 `未超过` は演算子テーブルにありません。
   次に、正規表現はベア `超过` と一致し、`未` を破棄します。 `不超过` という単語全体が `_LESS_EQUAL` に含まれます
   したがって、それは通ります - 純粋に語彙の不一致です。 `_NEGATION_RE`自体も欠落しています
   満たしていない/超えていない/下回っている/不十分である/はるかに下回っています。
2. **ユニットプレフィックスマッチング。 ** `_UNIT` には正しい境界がありません。`mV*s` は `mV` として照合されます。
   したがって、mV と mV・s は同じ次元として比較されます。

修正: エラーを報告する前に、一致範囲全体に対して `_NEGATION_RE` を実行します。否定的な単語のリストを完成させます。
`_UNIT` に右側の境界を追加して、`mV*s` / `mV·ms` が `mV` に折りたたまれなくなるようにします。

**このチェックを直接削除しないでください。 ** 完全な判定オブジェクト、11 個のトリガーを含む 632 個のコピーをスキャンしました。
**そのうち 10 件は実際のモデル エラーです** (「145 ミリ秒、通常の上限 (200 ミリ秒) よりわずかに高い」など)、
「63 bpm、頻脈の定義と一致 (>100 bpm)」)、Qwen のみが誤報です。
しかし、誤検知を引き起こす文パターンは、まさに診断を除外する場合の標準的な書き方です**。
したがって、最も影響を受けるのは通常の心電図です。
